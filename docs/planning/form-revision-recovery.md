# Published form revision recovery

Implemented increment: 2026-10-14 (Asia/Dubai). User-approved policy; pending merge gates. This increment does not complete the full form identity/lifecycle catalogue.

## Visitor and editor behavior

Generic Form and Contact Cards & Form load published questions and a server-generated revision fingerprint. If an editor publishes a changed question definition before a visitor submits, intake rejects the stale revision before storing answers or delivering notifications. The form refreshes in place, explains any cleared answers and focuses that explanation. Visitors review the new questions and submit deliberately; recovery never automatically posts another request.

Preserve an answer only when the field has the same unique nonempty row ID, the same control type and a value that passes the updated shared validation. Names/labels/order can change without losing compatible meaning. A select answer remains only while its value is still allowed. Removed/replaced fields, changed types, missing/duplicate IDs and newly invalid answers are cleared. New questions start empty (checkboxes false). These are in-memory answers only; no local-storage persistence or backfill is introduced.

## Runtime contract

- [Published projection](../../src/lib/genericFormRevision.server.ts) uses the same snapshot fingerprint as stored history; SHA-256 stays server-only. Public questions and the submit label cross the browser boundary, not private notes, recipients or confirmation configuration. The published-loader cache namespace changes to avoid reusing revisionless cached projections.
- [Transport](../../src/lib/submitGenericForm.ts) adds optional `formRevision` to the existing `{ values, metadata }` JSON request. Generic public adapters always supply it. A malformed supplied revision returns 400; mismatch returns 409 with `code: FORM_CHANGED`, a current public `form` definition and `Cache-Control: no-store`. A valid refreshed revision proceeds through ordinary validation and stores its snapshot.
- [Production form](../../src/components/revamp/generic-form.tsx) validates compatibility through [recoverFormAnswers](../../src/lib/recoverFormAnswers.ts), refreshes controls/label/revision, retains ordinary error/retry/pending behavior, and requires a new submission. Both blocks use the same engine. Disabled Live Preview never sends requests.
- Revisionless legacy Contact33 and fixed Review clients retain their current behavior; this is a compatibility boundary, not a claim that every legacy presentation is revision-protected. Renaming/removing/unpublishing a Form slug uses the existing unavailable-form flow. No new endpoint, collection, environment variable, dependency or database migration is introduced.
- The fingerprint is a content identity, not a Payload version ID or a secret authorization token. Intake compares the definition it reads for that request; there is no cross-document atomic-publication guarantee. Durable idempotency, private uploads, conditions, expanded controls, complete option lifecycle and export policies remain separate work.
