## Question

Which smallest capabilities and observed task gates are required before handing a
working website to client editors, and which catalogue enhancements can follow?

## Boundaries and expected evidence

The user confirmed team/Admin setup followed by client Site Managers on assigned
sections. Review the [proposed client roadmap](../../../docs/planning/client-website-delivery-roadmap.md)
and source baseline. Choose release gates for media ownership, account handoff,
first-page task, public publishing/navigation, recovery and launch. Distinguish
verify-existing work from actual gaps; retain advanced-forms deferrals and the
entire catalogue without treating all open boxes as release blockers.

This bounded first-client decision precedes, and does not replace, full-catalogue
phased release planning or broad onboarding acceptance. No new role, visual editor,
mandatory setup wizard, provider switch or feature implementation is implied.

## Comments

Charted on 17 October 2026. Release placement is proposed, not decided. The handoff
audience is confirmed input; no human release-policy answer has been invented.

### Answer — 17 October 2026

The user challenged the need for 242 features and explicitly accepted the proposed
five-goal first-client boundary: team setup, Page building, publishing/recovery,
client handoff and launch essentials. The [first-client checklist](../../../docs/planning/first-client-release.md)
is the active task selector; the complete catalogue remains reference backlog.
First demonstrate the existing full journey, fix proven blockers and observe a real
client before optional expansion. No per-feature acceptance box is completed by
this decision. Media/account details stay open. This records explicit user approval
following the five-goal proposal, not a claimed guided grilling interview.
